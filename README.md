# Fraud Detection System (Nigerian Banking Context)

A Flask web app that scores incoming transactions for fraud risk using a trained
RandomForest model, and lets staff review flagged transactions (Approve /
Investigate / Reject).

## Project layout

```
dataset/               credit_card_fraud_2026.csv (20,000 transactions, 1.7% fraud) — raw source data
src/
  features.py          shared preprocessing: remaps the raw CSV's US vocabulary to
                        Nigerian terms (NGN, Internet Banking/USSD/Mobile App, Visa/
                        Mastercard/Verve), used by both training and the app
  train.py             trains RandomForest + XGBoost, picks the better model, tunes
                        threshold, builds the merchant-risk lookup table
model/                  saved model, encoders, feature list, threshold, merchant
                        risk lookup (all generated by train.py)
reports/
  metrics_report.txt    full evaluation report (for the project write-up)
app/
  __init__.py           Flask app factory, DB + login setup, seeds a demo admin
                         user and 3 demo customers
  models.py             SQLAlchemy models: User, Customer, Transaction,
                         Prediction, Decision
  routes.py             login, dashboard, customers, new transaction, detail,
                         history — plus the auto-derivation logic
  inference.py          loads the saved model and scores a single transaction
  templates/            Jinja2 + Bootstrap UI
run.py                  entry point
requirements.txt
```

## Setup

```
pip install -r requirements.txt
python run.py
```

Visit http://127.0.0.1:5000 and log in with `admin` / `admin123` (seeded
automatically on first run, stored in `app/fraud_detection.db`).

## Retrain the model (optional — a trained model is already committed under model/)

Needs the extra training-only packages (xgboost, imbalanced-learn, matplotlib

## Deploying for free (Render + Supabase)

The app reads `DATABASE_URL` from the environment: if it's set, it connects
to that Postgres database; if not, it falls back to a local SQLite file. This
matters because most free hosts (Render included) wipe their local disk on
every restart/redeploy — so a hosted Postgres database is not optional once
this is deployed, even though SQLite is fine for local development.

**1. Push to GitHub** (see below), then:

**2. Create a free Postgres database on [Supabase](https://supabase.com)**
(no credit card required). New project → once it's provisioned, go to
Project Settings → Database → Connection string ("URI" tab, mode
**Session**) and copy it (starts with `postgresql://`), filling in the
database password you set when creating the project.

> Free Supabase projects auto-pause after 7 days with no activity. If the
> app shows a database connection error after a quiet week, open the
> Supabase dashboard and click **Restore project** — it only takes a
> minute, and doesn't lose any data. Fine for a project you show off
> occasionally; annoying if you needed it always instantly available, in
> which case Render's own free Postgres (auto-deleted after 30 days) or a
> paid tier would be the trade-offs to weigh instead.

**3. Deploy the web app on [Render](https://render.com)**:
- New → Blueprint → connect this GitHub repo (Render reads `render.yaml`
  automatically and sets up a free web service)
- In the service's Environment tab, add `DATABASE_URL` = the Supabase
  connection string from step 2 (`SECRET_KEY` is auto-generated by the blueprint)
- Deploy. First load after idle periods takes ~30–50 seconds to wake up —
  that's expected free-tier behavior, not a bug.

Every `git push` to the connected branch auto-redeploys.

## Design decisions made after initial feedback

**1. Nigerian context, not just relabeled currency.** The raw Kaggle CSV uses
US vocabulary (USD, "Online"/"Contactless" channels, RuPay/Discover cards).
`src/features.py` remaps this *before* encoding — so the model is actually
trained on Nigerian categories, not just displaying them cosmetically:

- Amounts converted to Naira (₦, ×1600 from the source USD figures)
- Channels: Internet Banking, POS, Mobile App, USSD, ATM
- Cards: Visa, Mastercard, Verve (RuPay/Discover/Amex merged into Verve —
  Nigeria's dominant local card scheme)
- Merchant categories given local flavor: Online Retail (Jumia/Konga),
  Streaming (Netflix/DSTV), Gaming/Betting, Utility Bills, etc.
- Demo customers and home states (Jigawa, Kano, Lagos, ...) for FUD Jigawa

**2. A Customer profile, so the transaction form isn't 23 fields.** Real bank
systems don't ask a teller to type a customer's age, card age, or account
balance on every single transaction — that data already exists on the account.
So:

- `Customer` holds the profile (name, account number, card type/age, customer
  age, balance, prior disputes, home state) — entered once via **Customers**.
- **New Transaction** only asks for what's actually specific to *this*
  transaction: customer, amount, merchant, channel, device, auth method, a
  location bucket (Same city / Same state / Different state / Outside
  Nigeria), CVV retries, and a handful of risk-indicator checkboxes.
- Everything else the model needs — `time_of_day_hour`, `day_of_week`,
  `hours_since_last_txn`, `txn_count_last_24h`, `velocity_score`,
  `merchant_risk_score` — is computed automatically at submission time from
  the server clock and the customer's transaction history (see
  `new_transaction()` in `app/routes.py`). `merchant_risk_score` comes from a
  per-category average risk table built during training
  (`model/merchant_risk_lookup.json`); `velocity_score` is a heuristic
  combining recent transaction count and recency, documented inline in the
  code — worth stating as a simplification in your report, since production
  systems would compute it from much richer historical behavior.

Three demo customers are seeded automatically (`app/__init__.py`) so you're
not stuck adding one before you can try the app.

## How it works

1. Staff pick or add a **Customer**.
2. On **New Transaction**, select that customer, fill in the transaction
   specifics (or click a demo preset — Likely Legit / Borderline / Likely
   Fraud), and submit.
3. The route auto-derives the technical features, assembles the full feature
   vector, and scores it with the model (`app/inference.py`).
4. Result: a risk score (0–100%) and a Flagged/Clear badge, shown immediately.
5. If flagged, staff record a decision (Approve / Investigate / Reject).
6. **Dashboard** shows totals/flagged/pending counts; **History** lists every
   transaction with its outcome.

## Modeling notes (see `reports/metrics_report.txt` for full numbers)

- **Class imbalance**: fraud is 1.7% of transactions. SMOTE is applied to the
  training split only (never the test split), so evaluation reflects
  real-world class balance.
- **Model choice**: RandomForest was selected over XGBoost purely on
  ROC-AUC (~0.75 vs ~0.68) on the held-out test set.
- **Threshold**: chosen to guarantee ~75% recall on the test set, not the
  default 0.5 cutoff. Rationale: a flagged transaction isn't auto-blocked —
  it goes to a staff member to review — so a missed fraud case (costs the
  bank money) is worse than an extra false alarm (costs a few minutes of
  staff review).
- **Top predictors**: merchant_risk_score, velocity_score, and auth_method
  dominate — consistent with known fraud indicators in the literature.
